# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user Telegram bot that relays messages to Claude and acts as an accountability/study buddy for a high school student. Everything lives in `bot.py`. All four planned phases are done: messaging, Claude replies, a task list that Claude manages through tool use, and scheduled check-ins. Reminders were added after that.

## Commands

```
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# create .env with TELEGRAM_TOKEN and ANTHROPIC_API_KEY (see README step 4)
python bot.py          # runs via long polling; no server or webhook
```

There are no tests, linter config, or build step. Requires Python 3.10+. Bot commands: `/start`, `/tasks` (lists open tasks, no API call), `/reminders` (lists upcoming reminders with ❌ cancel buttons, no API call), `/reset` (wipes chat history, keeps tasks and reminders).

- Run it from the repo root. `DB_PATH = "bot.db"` is relative, so starting it from another directory quietly creates a new, empty database.
- Only one process can poll a given token. If a second copy is running, you get a Telegram `Conflict` error.

## Testing

Changes are checked at three levels, cheapest first:

1. **Offline harness:** write a throwaway script in a scratch directory (not the repo) that does `sys.path.insert(0, <repo>)` and `import bot`, run with dummy `TELEGRAM_TOKEN=x ANTHROPIC_API_KEY=x` env vars. Because `DB_PATH` is relative, the scratch directory gets its own `bot.db`. Call the task helpers directly. To drive `handle_message`, build `update`/`context` from `types.SimpleNamespace`, with an async `reply_text` and `send_chat_action`. Replace `bot.claude.messages.create` with an async fake that returns scripted responses (objects with `stop_reason` and `content` blocks).
2. **Live API, no phone:** run the same harness without the dummy env vars. `load_dotenv()` finds the repo's `.env`, because it searches from `bot.py`'s directory, and the real Claude client is used. Wrap `bot.claude.messages.create` to print `usage` per call. Measured cost on Haiku 5.5 is about $0.0005 per message, tool rounds included.
3. **Telegram:** run the bot from the repo root and have the user message it, then confirm from the log. Tool calls are logged as `Tool <name> -> <result>`. A successful Claude call with no `Tool` line means nothing was saved or changed. Commands (`/tasks` etc.) don't touch the `messages` table, so the row count shows how many chat exchanges happened. To test a check-in without waiting for its time, call `send_checkin` from a harness with `context = SimpleNamespace(job=SimpleNamespace(data=kind), bot=telegram.Bot(TELEGRAM_TOKEN))`, run from the repo root so it uses the real `bot.db`. Sending doesn't conflict with a running poller. It messages the user's phone, so ask first.

## Architecture

- **Flow:** `handle_message` loads recent history from SQLite, appends the new user text, then runs a manual tool-use loop (up to `MAX_TOOL_ROUNDS`) around `claude.messages.create`. Inside the loop, each assistant turn goes back unchanged (thinking blocks included), with all tool results in one user message. Afterwards only the user text and the final text reply are persisted, together, by `save_exchange`; tool calls never reach the `messages` table. Persisting only after a successful reply keeps stored history strictly alternating user/assistant. Don't break that invariant, because `load_history` relies on it (it only trims leading assistant messages so the API sees a user turn first). If the API fails after a tool already ran, the database change stands and the reply says so. If Claude is still calling tools in the last allowed round, those tools run but Claude never sees their results; the reply is that response's text, which is often empty and falls back to "Done. Check /tasks to see your list."
- **Why a manual loop:** the SDK's Tool Runner is beta. The loop is short and keeps an explicit round cap.
- **Model settings:** the default model (`claude-haiku-5-5`) thinks by default, and thinking counts toward `max_tokens`, so `MAX_TOKENS` is 2000 with `effort: low`. Reply length is controlled by the system prompt, not `max_tokens`. That model rejects `temperature`, assistant prefill, and needs `tool_choice` left at the default `auto`. `output_config` needs `anthropic>=1.13.0`, which uses `httpx2`, not `httpx`.
- **Tasks:** `assignments` own ordered `steps`, and each step has its own mini-deadline. Dates are stored as `YYYY-MM-DD` text, so they compare as strings. Claude changes tasks through five of the tools in `TOOLS` (`save_assignment`, `complete_step`, `update_assignment`, `update_step`, `delete_assignment`, all `strict: true`; the other three are for reminders), which `run_tool` dispatches to plain helper functions. Helpers raise `ValueError` for bad input. `tool_result` turns `ValueError` and `KeyError` (a missing input field) into an `is_error` result so Claude can retry. Any other exception, such as one from `sqlite3`, escapes to the catch-all in `handle_message`. If that happens on the first tool, the student gets the "Couldn't reach Claude" reply. Every query is scoped to `chat_id` (steps through a join), so a wrong ID from Claude can't touch another chat's rows. An assignment's status is recalculated only when a step's `done` changes (`refresh_status`): it's done when the last step is done, and reopens when a step is reopened. Marking an assignment done marks its open steps done, but reopening an assignment leaves its steps alone, so it can be open with every step done.
- **No list tool:** open tasks with IDs are injected into the system prompt on each request by `tasks_for_prompt` (plain text, ISO dates), which saves a round trip on most messages.
- **History window:** `HISTORY_LIMIT = 20` rows, kept even so the window starts on a user message.
- **System prompt:** `build_system_prompt(chat_id)` is rebuilt on every API call, including each round of the tool loop, so it carries the current date/time in `TIMEZONE` and the up-to-date task list. Personality, style rules (short, text-message tone, don't write assignments for the student), and the task workflow live there.
- **Persona (product decision):** the student asked for a mean, roast-style coach. The prompt has it roast procrastination and excuses, never the student himself (no insults about intelligence, looks, family, or worth). It drops the act and is supportive when he seems genuinely stressed. The check-in prompts (`CHECKIN_PROMPTS`), their fallbacks (`CHECKIN_HEADERS`), and the `/start` reply use the same tone.
- **Task workflow (product decision):** when the student mentions an assignment, Claude proposes 2-5 steps as a keycap-emoji list and asks first. It calls `save_assignment` only after the student agrees. Live tests show Haiku 5.5 follows this.
- **Formatting:** Claude's replies are sent as plain text with no `parse_mode`, so the prompt forbids markdown. Telegram would show it as raw `**`/`#`, and enabling a parse mode for model output risks Telegram rejecting malformed markup. Only `/tasks` uses Telegram HTML (`tasks_for_telegram`: bold titles, italic due dates, ⬜/✅/⚠️ per step, strikethrough when done, sent with `ParseMode.HTML`). It's built in code, so any user-supplied text in it must go through `html.escape`.
- **Check-ins (product decisions):** `schedule_checkins` registers `send_checkin` with `app.job_queue.run_daily` for each entry in `CHECKINS`: morning at 7:00 on weekdays and 10:00 on weekends, the overdue nudge at 16:00, and the evening check at 20:00, all in `TIMEZONE`. PTB numbers `days` 0-6 as Sunday-Saturday. `checkin_facts` decides what each one covers: morning and evening cover open steps due today (morning also covers assignments due today), and the nudge covers overdue steps. If there's nothing to cover, nothing is sent. Each overdue step gets at most one nudge a day because only the once-daily nudge job mentions overdue steps, so there's no `last_nudged` column. `write_checkin` has Claude write the text: same model and system prompt, recent history plus one bracketed "[Scheduled check-in...]" user turn, and no tools. If the call fails, or returns no text, it falls back to `CHECKIN_HEADERS` plus the facts. Jobs have no `Update`, so they send to `int(ALLOWED_CHAT_ID)`, and nothing (check-ins or reminders) is scheduled when that's unset. Check-ins fire only while `bot.py` is running, and a run missed while the bot is down is skipped.
- **Check-ins and history:** check-ins are assistant turns with no user turn before them, so they go in their own `checkins` table, never in `messages`, which would break alternation. `checkins_for_prompt` puts the last 24 hours of them into the system prompt, so Claude knows what it sent when the student replies. `/reset` clears them along with the history.
- **Reminders (product decisions):** the student asks in chat, and Claude calls `set_reminder` right away, without the propose-and-confirm step assignments use. `update_reminder` and `delete_reminder` handle changes. Reminders can be one-time or repeat `daily`, `weekdays`, or `weekly` (weekly means the weekday of the first time). They're stored in the `reminders` table, where `remind_at` is the next time it goes off, as local `TIMEZONE` text `YYYY-MM-DD HH:MM`, so it compares as a string against `now_minute()`. When a one-time reminder goes off, it gets `sent_at` and stays in the table. A repeating one never gets `sent_at`; `next_occurrence` moves its `remind_at` forward and skips any times missed while the bot was down, so catching up sends one message, not a flood. `weekdays` reminders that would land on a weekend move to Monday. Delivery is the exact text (`⏰ text`) with no API call. `send_due_reminders` runs every minute via `run_repeating` (a second past the minute) instead of one job per reminder, so edits, cancels, and restarts need no job bookkeeping, and reminders missed while the bot was down go out late with "(meant for ...)". A failed send leaves the row pending, and the next minute retries it. Sent reminders are saved with `save_checkin(kind="reminder")`, so `checkins_for_prompt` shows them to Claude. Upcoming ones with `[reminder id]` go into the system prompt via `reminders_for_prompt`. `/reminders` builds Telegram HTML plus an `InlineKeyboardMarkup` with one `cancel_reminder:<id>` button per reminder. `cancel_reminder_button` (a `CallbackQueryHandler`) checks `is_allowed`, deletes, and redraws the message.
- **Access control:** `is_allowed` only replies to `ALLOWED_CHAT_ID`. When that is unset, `/start` replies with the caller's chat ID as a first-time setup step, and every other handler stays silent. Any new handler, including callback-query handlers for buttons, must check `is_allowed` first.
- **Storage:** `bot.db` (SQLite, gitignored) with `messages`, `assignments`, `steps`, `checkins`, and `reminders` tables, created by `init_db()` at startup with `CREATE TABLE IF NOT EXISTS`. Existing databases therefore gain new tables but **not new columns**; adding a column needs an explicit `ALTER TABLE` migration in `init_db`. Each helper opens its own short-lived connection. `messages.content` holds plain text and is passed straight to the API as message content.
- **Config:** loaded from `.env` via python-dotenv: `TELEGRAM_TOKEN`, `ANTHROPIC_API_KEY` (required), `ALLOWED_CHAT_ID`, `CLAUDE_MODEL` (default `claude-haiku-5-5`), `TIMEZONE` (default `America/Chicago`) (optional). The required vars are read at import time, so if one is missing the bot crashes on startup with a `KeyError`. There is no `.env.example`; README step 4 lists the variables.
- **Logging:** the `httpx` logger is raised to WARNING on purpose, because python-telegram-bot uses `httpx` and at INFO it logs request URLs that contain the bot token. Keep it that way. The Anthropic SDK's `httpx2` logger stays at INFO; its URLs contain no secrets.

## Roadmap

### Smaller follow-ups (offered, not decided)

- **Due date moves:** when an assignment's due date moves, Claude currently leaves the step deadlines alone. The prompt could have it offer to spread the steps out.
- **Hosting:** check-ins only fire while `bot.py` is running, so the bot needs an always-on machine (a Raspberry Pi or a cheap cloud host).
- **Out of API credits:** a billing error currently gets the generic "Couldn't reach Claude just now. Try again in a sec." reply, which is misleading because retrying won't help. Catch it to log a clear line and send a different message.
